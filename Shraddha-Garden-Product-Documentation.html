Executive SummarySection 0

0 · Executive Summary

Shraddha Garden Resort is a complete, production-grade digital platform for a luxury garden resort in Coimbatore. It is not a brochure website — it is an end-to-end hospitality operating system with three connected parts working as one product.

1 · The Guest Website

A beautifully designed public site where guests discover the property, browse stays and amenities, explore dining and events, read offers, and book and pay online in a guided multi-step flow. Guests can create an account and view their bookings.

2 · The Admin Portal

A secure staff back-office (/admin) to run the business day-to-day: bookings, availability & pricing, stays, marketing content, coupons, banners, reviews, enquiries, media, reports, users, payments and settings — with role-based permissions.

3 · The API & Data Layer

A secure server that holds all data, enforces the rules (who can do what, valid booking states, correct prices), talks to the payment gateway, and sends automated emails. The website and admin both rely on it.

Commercial Position

Replaces a stack of separate tools (website builder + booking engine + CRM + CMS + spreadsheets) with one owned platform, removing per-booking commissions charged by travel portals (OTAs).

The one-paragraph pitch (read aloud)

“Shraddha Garden Resort now has its own online front door and its own control room. Guests can find the property, fall in love with it, and book a stay with real online payment — in minutes, from a phone. Behind the scenes, your team manages every booking, price, offer and enquiry from a single secure dashboard, with a full history of who changed what. Because you own the platform, every direct booking avoids the 15–25% commission that booking portals charge — and the same system is ready to grow into multiple properties.”

Overall verdict. The product is feature-complete for a single-property direct-booking business and demonstrably well-architected (RBAC, server-authoritative payments, audit logging, state-machine-guarded bookings). The primary gaps before large-scale production are operational hardening — database scale, automated tests, monitoring and file-upload storage — detailed in Sections 9–12.

4.2 The pricing engine (why the number is trustworthy)

The price is calculated on the server, never in the browser. It starts from the stay’s base price-per-night, applies any matching rate rule for those dates (FIXED = set price, PERCENT = ±% of base, DELTA = ± flat amount, honouring minimum-stay and a priority order), rejects blocked dates, sums the nights, adds selected add-ons, subtracts a validated coupon (PERCENT with an optional cap, or FLAT, respecting minimum spend, usage limit and expiry), then adds GST per the Settings screen. The customer cannot tamper with any of this.

4.3 Server-authoritative payment (how real hotel engines work)

Booking
PENDING→ Create gateway
order→ Guest pays→ Verify signature
(HMAC)→ Booking CONFIRMED
+ PAID

The browser never marks a booking as paid. The server confirms it only after a cryptographically verified callback (HMAC signature) or a Razorpay webhook. Two providers sit behind one abstraction: Mock (offline test checkout, the default — great for demos) and Razorpay (real orders, refunds, HMAC-verified webhooks). This design prevents the classic fraud where a user fakes a “paid” response.

4.4 Booking status state machine

PENDING→CONFIRMED→CHECKED_IN→CHECKED_OUT    CANCELLED

Allowed moves are enforced on the server and mirrored in the admin UI: PENDING→CONFIRMED/CANCELLED; CONFIRMED→CHECKED_IN/CANCELLED; CHECKED_IN→CHECKED_OUT. Terminal states (CHECKED_OUT, CANCELLED) cannot move on. This prevents impossible transitions like checking out a cancelled booking.

Refunds are policy-aware. Cancel inside the free-cancellation window → full refund; outside it → the configured penalty is withheld. Issued from the booking drawer; the system cancels the booking and records a Payment row.

Admin PortalSection 5

5 · Admin Portal — Screen by Screen

5.0 Admin chrome (every admin page)

Sidebar — vertical navigation listing every admin section (Dashboard, Bookings, Availability, Stays, Amenities, Dining, Menu, Events, Offers, Coupons, Banners, Media, Reviews, Enquiries, Reports, Users, Settings, Email, Payments, Audit). Items the current role cannot access are hidden. Topbar — page context, signed-in user, and sign-out. PageHeader — title + primary action per screen. Shared UI kit: Badge, AdminButton, Drawer (slide-over panels), Field (labelled inputs), and DataState (loading/empty/error). A global axios client attaches the token and silently refreshes it once on a 401.

5.1 Admin Login /admin/login

Purpose: secure staff entry. Components: Email + Password fields, sign-in button, and one-click “fill” buttons for the three demo roles. Validation: wrong credentials show an error; success stores tokens and routes to the Dashboard. Roles & demo logins: Super Admin admin@shraddhagarden.com/Admin@123, Manager manager@…/Manager@123, Front Desk frontdesk@…/Frontdesk@123.

5.2 Dashboard /admin

Purpose: the at-a-glance health of the business. Components: KPI cards (totals such as revenue, bookings, enquiries), a revenue chart (6-month trend, Recharts) and a bookings-by-status breakdown. Data from GET /dashboard/stats. Loading/empty/error states throughout. Value: owners see performance without exporting anything.

5.3 Bookings /admin/bookings

Purpose: the operational core — manage every reservation. Components: a powerful data table (TanStack) with search (by name/code/email), a status filter, and pagination. Columns include code, guest, stay, dates, nights, guests, amount, status badge and payment badge. A row opens the Booking Drawer:

  • Detail view of the guest, stay, dates and money.
  • Status buttons that only offer legal next states (the state machine).
  • Payment actions (mark paid, refund — policy-aware; Manager+).
  • Notes and source (Website / Phone / Walk-in / OTA).

New Booking Drawer lets staff create a booking manually (walk-ins / phone) — pick stay, dates, guests; the server computes nights and amount.

5.4 Availability & Pricing /admin/availability (Manager+)

Purpose: control what can be booked and for how much. Components: an availability checker, a table of rate rules (name, stay or all-stays, date range, kind FIXED/PERCENT/DELTA, amount, min-stay, priority, active) with create/edit/delete, and a blocked-dates manager (date range + reason). Value: seasonal pricing, weekend premiums and maintenance holds — the levers a revenue manager needs.

5.5 Stays /admin/stays

Purpose: manage the room inventory. Components: a card grid of stays and a create/edit drawer form (React Hook Form + Zod) covering name, slug, badge, price, rating, intro, description, hero image, gallery, amenities, capacity, beds, inventory, featured & published toggles. Delete is Super-Admin-only and is blocked if the stay has bookings (protects historical records). Value: the property’s sellable catalogue is fully self-managed.

5.8 Coupons /admin/coupons (Manager+)

Purpose: run promotions. Fields per coupon: code, description, kind (PERCENT / FLAT), value, minimum spend, maximum discount cap, start/end dates, usage limit, used count, active. Value: measurable, controlled discounting with guard-rails against abuse (caps + limits + expiry).

5.9 Banners / Home content /admin/banners (Manager+)

Purpose: control the home page merchandising. Three banner types: ANNOUNCEMENT (the dismissible top strip), HERO (home hero slides), and PROMO (promotional banners, with a countdown from the end date). Each has title, subtitle, image, CTA label & link, active flag, sort order and scheduling. Value: time-boxed campaigns that switch themselves on/off by date.

5.10 Media /admin/media (Manager+)

Purpose: a central library of image URLs (with alt text and folder) reused across stays and content. Value: consistent imagery, one place to manage links. Limitation (see audit): currently URL-based, not direct file upload.

5.11 Reviews /admin/reviews (Front Desk+)

Purpose: a moderation queue for guest reviews (PENDING → APPROVED / REJECTED) with an optional public reply. Only approved reviews appear on the site. Value: protects brand reputation while showcasing genuine social proof.

5.12 Enquiries /admin/enquiries (Front Desk+)

Purpose: a lightweight CRM / leads inbox. Components: list of enquiries with status NEW → CONTACTED → CLOSED, an assignee, source, and a convert-to-booking action. Value: turns website enquiries into a trackable sales pipeline; nothing slips through the cracks.

5.13 Reports /admin/reports (Manager+)

Purpose: management reporting. Components: revenue, occupancy and booking-source breakdowns, with CSV export for finance/accounting. Value: board-ready numbers without a data analyst.

5.14 Users & Staff /admin/users

Purpose: manage the team. Components: user list with a role filter; create staff and change roles is Super-Admin-only. Value: onboard/offboard staff and enforce least-privilege access.

5.15 Settings /admin/settings (Manager+)

Purpose: global business configuration. Fields: GST / tax rate (feeds the booking price breakdown), contact information, and check-in / check-out times. Value: one place to keep legal/tax and operational parameters correct.

5.16 Email Settings /admin/email (Manager+)

Purpose: configure transactional email. The API includes a mailer, templates, a notify layer, and a scheduler that sends one-off reminders and review-requests (each booking records reminderSentAt and reviewRequestSentAt so nothing is sent twice). Value: automated guest communication — confirmations, pre-arrival reminders, post-stay review asks.

5.17 Payments /admin/payments

Purpose: configure how money is collected. Fields: provider (Mock / Razorpay), test/live mode, Key ID, Key Secret, Webhook Secret, enabled methods (card / UPI / net-banking / wallet), deposit %, and the cancellation policy. Security: secrets are editable by Super Admin only and are never returned to the browser — the public config exposes only the publishable Key ID. Value: go-live with real payments is a settings change, not a code change.

5.18 Audit Log /admin/audit (Super Admin only)

Purpose: accountability. Components: a chronological record of every admin mutation — actor, action, entity, entity id, timestamp. Value: answers “who changed this price / cancelled this booking / edited this user?” — essential for trust, disputes and (future) compliance.

Coverage note. Every admin screen shares the same three-state discipline (loading / empty / error), the same permission gate, and the same design language — the hallmark of a coherent, maintainable product rather than a collection of pages.

7.1 Request lifecycle (a booking, end-to-end)

  1. Guest submits dates & stay → React calls POST /availability/check.
  2. Server prices the stay (base + rate rules − blocks) and answers.
  3. Guest adds extras, details, coupon → React calls POST /coupons/validate, then POST /bookings/public.
  4. Server creates a PENDING booking & a gateway order (POST /payments/order).
  5. Guest pays → gateway calls back → POST /payments/verify (HMAC) and/or webhook.
  6. Server flips the booking to CONFIRMED + PAID, records a Payment row, triggers a confirmation email, writes nothing the browser could forge.
Honest note on deployment & ops. The code ships with an nginx config and deploy/update scripts, but there is no evidence of automated CI/CD, centralized logging, metrics/monitoring, or infrastructure-as-code in the repo. These are addressed as production-readiness items in §9–§12 rather than assumed to exist.

Negative AnalysisSection 10

10 · Negative Analysis (Brutally Honest)

Read this section as a friend, not a salesperson. Everything below is fixable, and none of it is unusual for a product at this stage — but a client deserves to hear it before signing.

Technical risks

  • SQLite is the biggest single technical risk. It is superb for development and a single small property, but it is a file-based database. Concurrency, backups and multi-server scaling are limited. This must move to PostgreSQL before serious volume.
  • No automated test coverage. Every future change is a manual-QA gamble. For a system that touches money, this is the most important thing to add.
  • Operational blind spot. Without logging/monitoring, the first sign of a payment or email failure may be an angry guest. Add error tracking (e.g. Sentry) and uptime monitoring day one.
  • Concurrency/idempotency. The payment verify path must be provably idempotent (a webhook can fire twice). This should be load-tested and confirmed, not assumed.

Business & UX risks

  • Content dependency. The product’s premium feel relies on high-quality photography and copy. Placeholder/Unsplash imagery must be replaced with real property shots before launch or the brand suffers.
  • No self-service booking changes. Guests who want to move a date must phone in — a friction point competitors solve.
  • Legal pages missing. Privacy policy, terms, cancellation/refund policy and cookie consent are prerequisites, not nice-to-haves, in India.
  • Single-property assumption. The data model is single-property. Expanding to multiple resorts is a real project, not a config toggle.
